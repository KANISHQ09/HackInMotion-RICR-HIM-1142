# Spendly AI Intelligence Service

The `ai/` directory contains Spendly's independent microservice for transaction data normalization, hybrid rule-and-LLM categorization, and financial intelligence.

## Reference vs. Hackathon Architecture

### REFERENCE INSIGHT
In the reference repository (`ezbookkeeping-main`), AI categorization and receipt recognition are embedded directly inside the Go backend (`pkg/llm`, `pkg/converters/ai`). The original implementation uses Go structs, template-rendered prompts (`templates/prompt/`), provider interfaces (`pkg/llm/provider/`), and direct SQL database insertion.

### NEW HACKATHON IMPLEMENTATION
For HackInMotion, we adapted these core architectural ideas into a standalone **TypeScript microservice** (`ai/`) with zero coupling to backend database engines:
- **Provider Abstraction**: A vendor-agnostic TypeScript interface (`LLMProvider`) supporting Google Gemini REST API, OpenAI API, and local mock testing providers.
- **Hybrid Pipeline**: A 4-stage cascade (Normalize → Rule Classifier → Confidence Check → LLM Fallback → Controlled Fallback).
- **HTTP REST API**: Exposed via lightweight Node.js HTTP server on port 3001 (`POST /api/v1/categorize`).
- **Zod Runtime Contracts**: Strict schema validation for transaction DTOs (`NormalizedTransaction`) and LLM output (`categoryPredictionSchema`).

## Architecture & Hybrid Categorization Flow

```text
Incoming Transaction Data (POST /api/v1/categorize)
                        │
                        ▼
           Stage 1: Transaction Normalization
     (normalizeMerchant, normalizeDate, Zod Schema)
                        │
                        ▼
        Stage 2: Deterministic Rule Engine
     (92 Merchant/Keyword Signals, Exact & Partial Matches)
                        │
                        ▼
         Stage 3: Confidence Threshold Check
               (Default Threshold = 0.70)
                        │
        ┌───────────────┴───────────────┐
        │                               │
[Confidence >= 0.70]           [Confidence < 0.70]
        │                               │
        ▼                               ▼
 Return Rule Prediction         Stage 4: LLM Fallback
  (method: "rule")            (Gemini REST API / OpenAI)
 0ms, Zero API cost                     │
                                ┌───────┴───────┐
                                │               │
                          [LLM Success]    [LLM Failure / No Key]
                                │               │
                                ▼               ▼
                         Return LLM Result   Controlled Fallback
                          (method: "llm")    (method: "fallback")
```

## Categorization Methods & Taxonomy

### Taxonomy (15 Expense Categories)
- `food`, `groceries`, `rent`, `bills`, `shopping`, `transport`, `travel`, `entertainment`, `healthcare`, `education`, `subscriptions`, `personal-care`, `insurance`, `fees`, `other`.

### Categorization Methods
- `"rule"`: High-confidence prediction from merchant signals (e.g., `Swiggy` → Food, `Netflix` → Subscriptions).
- `"llm"`: Prediction generated by Gemini/OpenAI for ambiguous or unknown merchants.
- `"fallback"`: Safe fallback prediction (`"other"`, confidence `0.20`) when evidence is weak and LLM is unconfigured or unavailable.

## Configuration & Environment Variables

Create or configure `.env` in `ai/`:

```env
# AI Service Network Settings
AI_PORT=3001
AI_HOST=127.0.0.1

# Intelligence Engine Settings
AI_PROVIDER=gemini           # Options: gemini | openai | mock
AI_CONFIDENCE_THRESHOLD=0.70 # Default threshold to trigger LLM
AI_LLM_TIMEOUT_MS=5000       # LLM API request timeout in milliseconds

# Google Gemini API
GEMINI_API_KEY=your_gemini_api_key_here
GEMINI_MODEL=gemini-1.5-flash

# OpenAI API (Optional Alternative)
OPENAI_API_KEY=your_openai_api_key_here
OPENAI_MODEL=gpt-4o-mini
```

> **Note**: The service operates safely without an API key. High-confidence rules run normally, low-confidence cases return controlled fallback predictions, and the server never crashes.

## HTTP REST API Documentation

### 1. `GET /health`
Returns system health status.

**Response (200 OK):**
```json
{
  "status": "ok",
  "service": "ai"
}
```

### 2. `POST /api/v1/categorize`
Classifies a transaction into a structured category.

**Request Payload:**
```json
{
  "transaction": {
    "id": "tx-101",
    "userId": "42",
    "amount": 450.50,
    "type": "expense",
    "date": "2026-08-13T10:00:00.000Z",
    "merchant": "SWIGGY",
    "description": "SWIGGY INSTAMART ORDER",
    "accountId": "1",
    "currency": "INR"
  }
}
```

**Response (200 OK - Rule Match):**
```json
{
  "success": true,
  "prediction": {
    "categoryId": "food",
    "categoryName": "Food",
    "confidence": 0.97,
    "method": "rule",
    "matchedSignals": ["swiggy"],
    "reason": "Matched keyword/merchant signals: swiggy"
  }
}
```

**Response (200 OK - LLM Match):**
```json
{
  "success": true,
  "prediction": {
    "categoryId": "subscriptions",
    "categoryName": "Subscriptions",
    "confidence": 0.92,
    "method": "llm",
    "matchedSignals": [],
    "reason": "Identified cloud infrastructure subscription service."
  }
}
```

**Response (400 Bad Request):**
```json
{
  "success": false,
  "error": "Transaction validation failed: Amount must be a valid finite number"
}
```
